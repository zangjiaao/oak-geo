# 第一部分 · 方法论

GEO 的完整流程是七步：**找词 → 出题 → 测留白 → 排机会 → 写内容 → 分发 → 验证回流**。这一部分按七步讲清楚每一步怎么做、判断标准是什么。

## 1. GEO 和 SEO 差在哪

一句话：**SEO 是让人搜到你，GEO 是让 AI 回答时愿意摘抄你、并且抄得对。**

先承认一个事实：现在的模型回答新问题，基本都是先搜索再作答。所以搜索排名确实是上游，GEO 和 SEO 在"动作"上大量重叠——都要选词、都要发内容、都要建权威。差别不在动作，在下面这张表：

| | SEO | GEO |
|---|---|---|
| 优化目标 | 排名和点击 | 被模型摘抄、且抄得对 |
| 测量对象 | 排名、搜索流量 | 模型答案本身：有没有提你、引你、说对 |
| 内容标准 | 能排名的页面 | 能被整段抄走的事实块（有数字、有口径、有边界） |
| 防守能力 | 无 | 能发现"AI 把你的参数、价格说错了" |
| 客户是谁 | 要流量的人 | 要答案份额的品牌 |

**判定一种做法是不是注水，标准只有一条**：内容是**为算法写**还是**为交付写**。为算法写的薄页面（蹭词、堆链接、没事实）就是注水；有真实事实、经得起核对的内容，动作再快也不算注水。

顺手把另一个易混对象也说清：**舆情监测**看全网声量、做预警，产出喂给公关；我们看固定问句下的模型回答、测"答得对不对"，产出喂给内容。不做声量、不做情感分析、不做负面预警。

给客户讲的版本："别人在往模型里灌他们的口径，你的事实没人核对。我们做的是答案侧的测量和事实纪律。"

## 2. 找需求：词从哪来

不要先想"我要做什么产品"，先看市场在搜什么。词有四个来源：

| 类别 | 来源 | 拿到什么 | 毛病 | 权重 |
|---|---|---|---|---|
| A 检索类 | Google Trends、百度指数、5118 等 | 检索热度、相关词、趋势 | 只反映"主动搜"，不反映"问 AI" | 30% |
| B 平台内 | 知乎热榜与问题关注数、小红书/抖音/亚马逊等站内下拉与联想 | 平台里的真实问句 | 各平台口径不一，要爬 | 15% |
| C 自有一手 | 客服工单、聊天记录、站内搜索日志 | 客户的原话，独家 | 只覆盖已有客户；要打通数据 | 30% |
| D AI 实测 | 直接问主流模型，记录回答 | 唯一能直接看"AI 现在怎么答" | 结果不稳定，要重复采样 | 25% |

A 和 C 并列最高：A 是唯一能跨行业比较的（决定先做哪个行业、哪个词）；C 是唯一拿到真实客户语言的（**没有 C 类反哺的行业，留白结论不对外引用**）。

**词怎么来：种子表 + 生成语法。**

每个行业维护一张种子表（50–100 个词根），包含品类词、场景词、问题词根、竞品名、自家品线。品类词单独归类（后面判断"回答有没有点名厂商"要用）。种子表每行必须有维护人和复核时间——**没有维护人的行业不开管道**。

除了人工列举，用组合模板批量造词：

| 模板 | 例子 |
|---|---|
| [功能] + generator | bio generator、prompt generator |
| [格式A] to [格式B] | webp to png、pdf to docx |
| [行业] + calculator | cagr calculator、macro calculator |
| [大牌] + alternative | notion alternative、canva alternative |
| [游戏名] + unblocked / online | 海外学生搜索量巨大 |

**热度只分档，不报绝对数。**指数工具给的是指数不是搜索次数，跨词跨行业不可比。产品只输出：热度档 S/A/B/C（S≥行业 P90，A≥P75，B≥P50）+ 趋势方向 + 4 周环比。界面和销售材料一律不许出现"月搜索 X 次"，数据表里也不设这个字段。

**飙升告警**：新词首见不满 14 天、且连续两周环比上升，直接进候选预筛。风口是按天爆的，等季度重算就晚了。

**哪些行业先做**：14 行业打分表（见 `GEO行业优先级.csv`）只是内部排产表，不进产品逻辑、不进对外报告。行业分 ≥4.5 的开管道（当前：B2B、汽车、医疗）；4.0–4.5 只建种子表；更低只观察。

## 3. 出题：把词变成可测量的问句

词池负责"找"，问句池负责"证"，节奏必须分开：

| | 词池 | 问句池 |
|---|---|---|
| 节奏 | 每周刷新 | 按版本冻结，平时不动 |
| 作用 | 发现新机会 | 证明动作有效（前后可比） |

问句池是测量资产，三条规则：

1. **每条问句必须带出处**（来自哪个词、哪个源、谁采的）。没出处的问句不进池——否则复测出涨跌，分不清是内容起效还是题目换了。
2. **冻结后不可改**。改题、换模型、加减句，一律开新版本，旧版只读保留。基线和复测必须用同一版本；版本不一致就是"不可比"，不出差值、不进报告。
3. **意图分六类**，每簇打标：

| 意图 | 例句 | 决策阶段 |
|---|---|---|
| 认知 | 什么是 GEO | 早期 |
| 选型对比 | A 和 B 哪个好 | 中期 |
| 价格 | 多少钱一年 | 中期 |
| 场景方案 | 某行业怎么做 | 中期偏后 |
| 排障 | 没效果怎么办 | 后期 |
| 替代/否定 | 是不是智商税 | 决策临界 |

**问句从哪来**：测量问句不用生成语法造（语法只造词），优先用市场上真实问过的话——知乎问题原文、平台搜索表述、客服工单原话（可略改写但保留原意与出处）。理由：测的就是用户真正会问 AI 的问法，且真实问句有出处可溯源。V1 的 LLM 起草问句也只是“从簇内真实表述改写”，不是凭空生成。

**可比性的单位是“簇的问句集”，不是整池**：新候选簇加入会开新的 `question_pool_version`，但只要老簇自己的 3 条问句没动，老簇的基线差值照样可比——否则每加一个新簇就得全量重开基线，运营上不可行。

**问法漂移的人工阀门**：同一簇的新表述热度超过代表问句时（词池周批可检出），由策略决定是否升级问句；升级 = 开新版本 + 重开基线（旧数据标不可比保留）。换问句代价大（基线作废），必须人工拍板，不做自动换题。这是“可比性 vs 时效性”的显性取舍：新需求从出现到测完，正常时滞 2–5 周（周发现 + 月确认），与内容生产周期相当。

## 4. 测留白：模型现在答得怎么样

留白度 = 一个意图簇的"可趁之机"，由四部分组成（注意：**空白度只是四分之一**，别和留白度混用）：

| 判定 | 看什么 | 打 1 的情形 |
|---|---|---|
| 空白度 blank | 回答有没有点名任何厂商 | 没点名任何厂商（纯定义、泛泛而谈） |
| 错答度 error | 有没有错误事实（价格、资质、参数、适用人群、承诺，五类高危） | 错误率高，或出现"把竞品参数写成自家" |
| 泛化度 generic | 有没有具体内容（名称/带单位数字/边界/可执行步骤，四项各 1 分） | 通篇"因行业而异" |
| 竞品占位度 competitor | 本品牌 vs 最强竞品的提及率 | 本品牌零提及且最强竞品 ≥60% |

互斥规则记两条：回答里出现竞品名就不算空白（由竞品占位记）；既错又空泛可以并存。

**采样口径**（MVP）：每簇 3 条问句 × 4 个国内模型 × 温度 0/0.7 × 3 轮 = **72 条回答**；拒答单独记，不算分母。扩展态：5 国内模型 + 2 国际、轮次升 5。

**双轨口径（v3.3）**：裸 API 与网页端行为差异巨大——网页端默认检索接地，裸 API 只反映预训练知识，永远测不出“引用”。两条轨道分开测、分开报：

| | 检索轨（主轨，对外口径） | 记忆轨（辅轨，防守视角） |
|---|---|---|
| 怎么测 | API + 各家原生联网工具 | 同一批模型裸 API（关联网） |
| 测什么 | 提及、引用、SOV——对齐用户真实看到的答案 | 预训练知识里的提及与错答 |
| 客户问题 | “当下答案里有没有我” | “模型学到的是不是我错的” |
| 解法 | 内容发布与渠道分发 | 语料建设（见效慢） |

记忆轨的错答多来自预训练污染（参数、价格记错），是事实准确率的主战场。**选型硬标准：被测 4 家必须 API 原生支持联网**（通义 enable_search、豆包联网插件、智谱 web_search、混元搜索增强；无联网的不进被测集，可作 judge 候选——选型时以各家当期文档为准核实）。`scoring_snapshot.grounding_mode` 与温度轮次一起冻结，**换轨 = 换快照 = 基线重置，同一快照内不混轨**。MVP 成本不变：检索轨为主；记忆轨仅对建议的 3 簇加测（36 条/簇，约 ¥3/客户），作诊断包增值栏目。

**网页端校准**：月度抽 5–10% 问句在网页版复跑（**Playwright 半自动 + 人工复核**），记录与 API 检索轨的提及判定偏差率，写进报告附录——诚实披露口径差异，不假装一致。

**浏览器直采不进主轨（v3.4 拍板，常见提案明确否决）**：①网页端无法控制温度/轮次/模型版本（灰度滚动且不透明）——快照不可复现，“复测可比”作废（硬规则 2）；②自动化消费级 UI 违反平台条款，规模化必然依赖账号池，踩中合规红线；③量级不可行：基线 2,160 条 + 月度 3,456 条，浏览器采一条 30–60 秒，一次基线即 18–36 小时连续浏览器时间，且穿插验证码/限流；④“省检索成本”是错觉——主轨 API 全部预算 ¥104/月，而 4 家消费级 UI 每周改版的选择器维护是跑步机，真实成本远高于 token 费。Playwright 的位置就是校准轨：低频、少量账号、人工陪同；只有 App/网页、无可用 API 的助手也只进校准轨，不进被测集。

**省钱的前置过滤：结果页真空度。**跑 72 条回答是有成本的，先用便宜信号筛一遍：搜索结果前 20 条里独立产品站占比低、论坛碎屑多、官方供给弱，就算"结果页真空"。因为模型接地于搜索，**结果页真空大概率先导于模型空白**——这是一个待验证的假设（拿 D 类探针验证），但值得作为候选簇的第二道筛选：只有"热度档高 + 结果页真空"的簇才花探针钱。

**打分怎么算怎么存**：回答级记档位 {0, 0.5, 1} → 问句级记连续值（4 位小数）→ 簇级 `raw` 取均值、`score` 取三档（0.25 进 0.5，0.75 进 1）。raw 留着校准用，score 给人看。字段见 §18。

**四条铁律**：同快照只写一次，重跑开新快照；快照必须能还原问句原文、模型清单、采样参数、评分脚本版本；样本不足（`n_valid < 10` 或模型覆盖 < 3）不出分，显示"待补测"，**不许拿 0 或均值凑**；实际跑了几个模型就记几个，不折算。

## 5. 排机会：先做哪个

两条排序规则，先粗后细：

1. **热度档是第一排序键**。先按 S/A/B/C 排，同档内才用机会分；跨档不比分数。没有检索数据的词只能进"待补量"队列，不许排产。
2. **机会分**：`Score = 0.25·需求规模 + 0.35·留白度 + 0.25·商业价值 − 0.15·竞争密度`

**四个权重目前是假设，没有数据支撑，不许当结论讲给客户。**校准方法：补测到 100 个词，人工标"值不值得做"和优先级 1–5，拟合权重；模型 TOP20 与人工 TOP20 重合率 ≥70% 才能从 v0 升 v1。校准完成前，机会分只用于同档内排序，不进报价和对外材料。

已知缺陷：竞品占位同时出现在留白度和竞争密度里，重复计数，校准时二选一（建议留白度留 competitor，竞争密度改用"占位方数量"）。

## 6. 写内容：事实块

GEO 内容的最小单元不是文章，是**事实块**——一段模型愿意原样摘录的话。写完过四问：

1. 有具体数字吗？（没数字的形容词删掉）
2. 数字有口径吗？（时间、样本、统计范围）
3. 有可追溯的出处吗？
4. 有边界条件吗？（什么情况下成立 / 不成立）

标准示例：

> 2025 年中国 GEO 优化服务市场规模约 28–29 亿元，统计口径为服务商基础优化服务营收（秒针、艾瑞/IDC），时点为 2025 年全年，方法论可追溯。

口径纪律：对外只用 28–29 亿这一个数；不许并列宽口径做倍数比较；引用四件齐（机构 + 口径 + 时点 + 链接），缺一不发。

反面教材两则：`市场规模巨大，正处于爆发前夜`——没有引用价值；`窄口径 28 亿，宽口径 560 亿，相差 20 倍`——把不该对外的数带出去了。

**意图决定内容形态**（硬映射，不自由发挥）：

| 意图 | 形态 | 必须有的事实块 |
|---|---|---|
| 认知 | 定义页 | 定义、边界、与相邻概念区别、常见误解 |
| 选型对比 | 对比页 | 维度表、适用/不适用场景、价格区间、参数 |
| 价格 | 报价页 | 区间、计价单位、影响因素、隐藏成本 |
| 场景方案 | 方案页 | 步骤、角色分工、周期、可量化目标 |
| 排障 | FAQ | 症状—原因—动作三段式 |
| 替代/否定 | 论证页 | 反面证据、失败案例、什么情况别做 |

文章组织：`标题 → 结论段（3 句内先给答案）→ 3–6 个事实块 → 边界与反例 → 出处列表`。结论放开头是因为模型爱摘开头；出处放最后，方便它连引用一起搬。

**块的粒度与类型**：一块只承载 1–2 个事实、50–150 字，不写大墙——块越大，模型检索越难整段匹配。块的类型由承载的事实性质决定：数字块、边界块、对比块、反例块（结论段是特殊的汇总块）。§6 推导规则表里每个意图的“必须有的事实块”清单，在编辑器里就是**提交闸门**——必配类型缺一块，文章发不出去。

**两条编辑器级校验**（把口径纪律机械化）：①**段落自包含**——块内不许出现“如上文所述”“见表”这类悬空指代，被模型单独切走后全部失效，每块必须自带完整口径；②**跨平台口径冲突**——同一数字+单位的块在多处版本不一致时系统报警（模型交叉印证发现口径打架会降权）。

**发布的结构要求**：每个块发布成独立 DOM 区块、带描述性小标题，维度对比用真表格标签，问答类挂 FAQ Schema——让模型检索的切分正好落在预设的块边界上。

**来源分三级**：L1 一手（官方文档、财报、标准原文、自有数据）；L2 二手可信（机构报告、主流媒体调研）；L3 不可用（无源转引、软文预测）。**L3 一律不许进事实块**。

## 7. 分发：发到哪里

按"被模型采信的概率"排，不是全网铺。当前排序依据是 12 个实测词的结果页占位（弱实测、样本小，只能当起点）：

1. **厂商自有官网**——唯一口径完全自控的渠道，实测多次进前五；技术要求：结构化、可抓取、带 FAQ Schema。
2. **知乎**——出现率最高的单一平台，跨三个行业都在。
3. **垂直媒体 / 行业站**（含维基类、行业协会）——占专业解释位，比综合媒体更像“可被引用的权威源”。
4. **政府 / 公立 / 学术机构**——出现少但后验价值最高，本身就是事实源。
5. **AI 工具目录**（Toolify、There's An AI For That 等）——模型答"推荐工具"类问题的高频引用源，提交成本几乎为零。
6. **权威媒体 / 研报**——控"同源稿多站投放"，会被当内容农场降权。
7. **视频文字稿 / UGC**——模型越来越多读多模态文本，但样本少且最不可控，排后。

两条纪律：同一事实块跨平台**口径必须一致**（模型会交叉印证，口径打架就降权）；"谁占了搜索结果页"是实测，"模型采信谁"仍是假设——等自己内容被引用的数据攒够 30 条，再用实测命中率重排。

**簇级渠道信号（v3.2 新增）**：全局排序只是兑底。两个更强的信号在评分批次里顺手产出，零新增成本：①**簇级模型引用分布**——72 条回答中被模型引用的域名计数（搜索接地的模型常自带来源标注），直接观测“模型在这个簇上信谁”；②**簇级结果页占位**——真空度预筛抓的前 20 条结果的平台构成（现在只拿它算真空度分就扔了）。机会卡因此新增渠道信号区：

```
机会卡 · 渠道信号
├─ 模型引用：知乎 12/72、厂商官网 6/72、垂直媒体 3/72
├─ 结果页占位：知乎 7/20、论坛 9/20、厂商官网 0/20
└─ 建议：官网（口径自控，必选）+ 知乎（双信号高）
```

合成规则（信号强度降序）：簇级模型引用 > 簇级结果页占位 > 全局基线排序 > 意图类型修正（认知类偏官网与百科型源、价格类必须官网、排障偏 FAQ）。厂商官网永远在建议里（口径自控的固定规则），簇信号只决定第 2、3 位。落库见 §18 `cluster_platform_signal`。证据边界：簇级引用是实测但样本小（72 条中十几条），占位实测但“占位≠采信”——建议永远标“建议 + 证据计数”，不写“XX 平台最容易被 AI 引用”。

## 8. 验证与回流：怎么证明有效

**先打基线（T0）**，否则 D+30 的涨跌没有参照，所有"提升"都不可证。

**复测口径**（与 §4 采样同源）：

| | MVP | 扩展 |
|---|---|---|
| 频率 | D+3 / D+14 / D+30 事件复测 + 月度全量 | 同 |
| 事件复测范围 | 目标 3 簇 + 对照 3 簇（6 簇 × 72 = 432 次/轮） | 按监测簇数 |
| 月度全量 | 30 簇 × 72 = 2,160 次 | 同 |
| 参数 | 3 问句 × 4 模型 × 2 温度 × 3 轮 | 5 模型 + 国际 2 个 |

**必须有对照组**（没做动作的簇），用来剥离模型自身更新带来的漂移。

**预期管理**：效果是滞后的（类似搜索的沙盒期），D+3 / D+14 大概率看不到变化，以月度为准——这句话要提前讲给客户，别让他在 D+14 看到零引用就慌。

**指标六件套**：

| 指标 | 定义 | 用法 |
|---|---|---|
| 提及率 | 回答中出现品牌名的比例 | 入门 |
| 引用率 | 回答引用了自有事实块的比例 | 核心 |
| 答案排位 | 品牌在列举式回答中的位置均值 | 辅助 |
| 事实准确率 | 正确事实数 / 涉及本品牌的事实总数 | 防守核心 |
| 可见度份额 SOV | 本品牌提及 /（本品牌 + 竞品提及） | 对外主指标 |
| AI 线索（软归因） | 带来源标记的 AI 场景落地页转化 | 续费依据（V1.x） |

**这条 ID 链让我们能回答三个别人回答不了的问题**：哪条内容被哪个模型在哪类问句里引用了（内容级归因）；某事实块被引用后，答案正确率有没有上升（块级有效性）；某个簇的可见度提升，是哪几条内容共同作用（组合效应）。答案都藏在 `cited_claim_ids` 里。

**归因要诚实**：AI 线索只做软归因（专属落地页、专属优惠码、对话式入口），不承诺精确归因。

**回流五类**(每类带触发阈值和责任角色,否则就是口号):

| 信号 | 触发条件 | 动作 |
|---|---|---|
| 写对了没被引用 | 连续 2 期引用率 <10% 且提及率在升 | 先改结构和平台（≤2 轮），仍无效则降权该内容 |
| 被引用但说错 | 准确率 <90%，或混入 L3 来源 | 24 小时内下线或修正，追溯同源的其他块 |
| 没人问 | 三个条件同时满足：需求分位后 20% + 探针全泛化 + 平台月出现量低于阈值 | 软删除归档，不物理删 |
| 竞品新占位 | 占位度 <0.5 升到 >0.8 且连续 2 期 | 重开机会卡，排下期 |
| 模型大版本更新 | 事件触发，不等周期 | 全量重跑基线，标"基线重置"，不与旧期直接比 |

**删簇之后词池重算**（按顺序）：软删除保留历史 → SOV 分母保留 90 天过渡 → 按机会分补位、保持簇数恒定（默认 30 簇/品牌/期）→ 一期变动超过 20% 先暂停补位、复核种子词。删簇是最贵的误判，三个条件只满足两个的标"观察"，不删。

# 第二部分 · 产品设计

先看全貌（§9），再按三层拆开（§10–§12），然后是界面与页面设计（§13）、MVP（§14），最后是智能化与对外接入（§15–§16）。

## 9. 产品总览

**做**：一套让品牌在 AI 回答里"被提到、被说对、被引到正确场景"的全链路闭环工具。
**不做**：SEO 工具套壳、舆情监测系统、内容农场。

产品是一个系统三层：**需求层找机会 → 生产层做内容 → 验证层测效果**，层与层之间靠 ID 链串起来。

```
┌──────────────────────────────────────────────┐
│ 需求层　找机会                                │
│ 行业管道 → 词池 → 意图分层 → 问句池 → 留白评分 │
└───────────────┬──────────────────────────────┘
                │ 机会卡（Opportunity Card）
┌───────────────▼──────────────────────────────┐
│ 生产层　做内容                                │
│ 选题 → 事实块 → 来源灯 + 事实审核 → 分发      │
└───────────────┬──────────────────────────────┘
                │ 内容资产（带溯源 ID）
┌───────────────▼──────────────────────────────┐
│ 验证层　测效果                                │
│ 基线探针 → 多模型复测 → 引用溯源 → 对照归因   │
└───────────────┬──────────────────────────────┘
                │ 缺口回流
        ┌───────┴────────┐
        ▼                ▼
 回需求层（弃簇重算）     回生产层（改稿、补来源）
```

**ID 链**：问句有 `question_id`，机会卡有 `opportunity_card.id`，事实块有 `claim_block.id`，探针结果回写 `cited_claim_ids`。层与层之间传的是带 ID 的结构化对象，不是文档——断了这条链，产品就散成三个互不相干的工具。

**四条全局纪律**：

1. **审核在分发之前**。来源灯和事实审核不放行，就不进分发排期，不存在"先发后审"。
2. **基线先行**。没有 T0 基线，任何"提升"都不可证。
3. **回流两路**。"没人问"回需求层弃簇重算；"被引用但说错"回生产层改稿补来源。
4. **快照可比**。基线与复测必须用同一份问句与采样快照，口径不一致直接标"不可比"。

### 9.1 交付形态（v3 定稿）

产品做**全链路**：诊断 + 生产工具 + 验证复测，三层都在一个系统里，客户端开放编辑器。**但发布动作留在客户侧**——系统提供渠道适配建议和发布登记，不代发。代运营 / 代发 V1.x 再评估。

为什么不代发：自己写、自己发、自己测，复测结果就没有公信力。发布权在客户手里，"不承诺被 AI 推荐"这条边界才立得住（我们只承诺证据可复核、复测可比，不承诺排名、引用率、"包上"）。

| 使用模式 | 说明 |
|---|---|
| `full` 全链路 | 诊断 + 编辑器 + 审核流 + 复测，主力形态 |
| `diagnosis` 只读诊断 | 基线探针 + 缺口清单 + 3 簇建议 + 模板，入口 / 轻量形态 |
| `self` 自用 | 我方内部种子案例跑整包（含自己站的发布），产出可对外讲的案例 |

销售节奏沿用初版思路：**诊断档做入口**（轻、快、建立信任），跑通一条链路后升级全链路档。

**行业管道的经营属性**

行业管道（种子表/词池/归簇/分档）是按行业键组织的跨客户共享资产，成本随行业数摊销；看板是这台产能的仪表盘；机会卡是留白测量的量化载体。
三档变现分层：内部雷达（产能自用）/ 行业月报（获客内容资产，免费对外）/ 机会测量（付费核心）。行业月报不构成产品线，只是管道副产品。

### 9.2 利益冲突隔离（既生产又验证，运动员和裁判必须分开）

1. **事实审核独立放行**：FactCheck 是唯一放行权，放行对象包括我方生产的事实块；建包的人和放行的人不能是同一个。
2. **披露**：我方生产的内容，复测报告必须标注"内容由我方生产"，且必须带对照组。
3. **口径锁死**：采样参数与指标定义由第三部分统一锁死，不因客户或项目改。

### 9.3 角色与权限

| 角色 | 归属 | 能干什么 |
|---|---|---|
| 客户-决策者 Owner | 品牌 | 看本品牌诊断包 / SOV / 准确率 / 复测史；确认 3 个优先簇；提异议；续费 |
| 客户-执行者 Editor | 品牌 | 用事实块编辑器撰写与提交；下载模板与证据包；在自己渠道发布后回填登记 |
| 客户-只读 Viewer | 品牌 | 看报表与趋势，导出 |
| 我方-策略 Strategist | 我方 | 建机会卡、定词池版本、出缺口清单与 3 簇建议 |
| 我方-内容 Content | 我方 | 撰写事实块（服务档），受审核放行约束 |
| 我方-证据 Evidence | 我方 | 建证据包与模板、来源初检 |
| 我方-审核 FactCheck | 我方 | 唯一放行权：证据包、诊断结论、进分发的事实块 |
| 我方-客户成功 CS | 我方 | 排复测、出交付包、处理异议与工单 |
| 我方-管理员 Admin | 我方 | 租户、模型配额、审计日志 |

**竞品数据可见性**：聚合层（SOV 分母、占位度评分、被引域名分布）全员可见；竞品原始回答全文只限我方内部；客户对某条结论有异议时，可指名 `probe_id` 单条调阅（CS 陪同、水印、不可导出、写审计日志）——**单条可查，批量不可导**。

**租户**：一份合同 = 一个租户，租户下多品牌；MVP 单租户单品牌单行业，技术上多租户单库、`tenant_id` 行级隔离；跨租户只出脱敏行业基准，样本少于 5 个租户不出基准；私有化部署不在 V1。

**合规五条**：C 类数据要客户书面授权 + 入库自动脱敏 + 解约 30 天内删除；D 类只走官方 API，不搞账号池；B 类只取公开内容、遵守平台条款；所有原始回答与 C 类数据的访问写审计日志；对外材料不得出现"排名 / 引用率承诺"字样。

**界面(五 + 一)**:机会看板、诊断交付台、事实块编辑器、复测台、报告页,外加模板库。桌面优先(≥1440 宽),移动端只推日报卡片(今日新增错误、待审项)。页面设计详见 §13。

### 9.4 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| 模型快速迭代，昨天的结论今天失效 | 高 | 所有指标带时间戳与模型版本，只讲趋势不讲绝对值 |
| 平台反爬 / 反 AI 抓取政策收紧 | 高 | 优先自有渠道（官网、官方文档），不把命押在第三方平台 |
| 模型厂商服务条款变化（D 类采样依赖 API） | 中 | 只走官方 API，不用账号池；条款变化时降频或换模型 |
| 客户期待“包排名” | 中 | 合同里写清交付 SOV 与事实准确率，不承诺位置 |
| 内容被判定为操纵模型 | 中 | 全部事实块真实可核，不写假参数；这条是底线也是差异化 |
| 归因失真 | 中 | 只做软归因，明确写“参考值” |
| 提示注入（Agent 读外部内容被埋指令） | 中 | 外部内容只作数据、不进指令位（§15.3） |

## 10. 需求层设计

先看这一层的运行节奏（三条时钟），再讲接入收什么、管道怎么实现，最后是产品化要点。

### 10.1 三条时钟

```
┌─ 每周 · 词池日 ──────────────────────────────────────┐
│ A/B采集 → 去重归簇(稳定ID) → 打标 → 分档 → 快照v+1    │
│   → 飙升告警 → 候选队列(S/A档+真空度双筛) → 卡排序刷新 │
└──────────────────────┬───────────────────────────────┘
                       ↓ 每月 · 评分日（接入期加急）
┌──────────────────────┴───────────────────────────────┐
│ 候选簇配问句(问句池版本) → 探针72条/簇 → 判定 → 分数   │
│   → 机会卡补留白分与渠道信号 → 机会分 → 3簇建议        │
└──────────────────────┬───────────────────────────────┘
                       ↓ 事件驱动（第三条时钟）
  C类工单批次回灌 ｜ 客户发布→D+3/14/30复测 ｜ 模型版本变更→基线重置
```

**周时钟管风向（看“量”往哪走），月时钟管机会（验“质”值不值），事件时钟管验证。**市场变化经三条路进来：新需求冒头→新簇配新问句入测（最坏 2–5 周滞后，与内容生产周期相当）；需求衰退→删簇归档；问法漂移→人工阀门（§3）。问句池不是建租户时建的，也不是每周刷新的——它是“某个簇要被测量了”才出现：簇进候选队列后配 3 条真实表述问句，冻结成版本，此后该簇的基线与复测都用它。

**走读示例（虚构客户“简造 ERP”，簇 C-107）**：第 1 周词池日，“ai 自动排产”首见、C 档、静默；第 2–3 周相关词激增、连续两周环比升→飙升告警，升入 S 档；SERP 前 20 无一家厂商页（真空度高），双筛通过进候选；加急评分批次配 3 条真实问句（知乎原文、联想词、工单改写）→ 72 条回答 → 空白 0.5、竞品占位 1（甲智造 63%、简造零提及）、错答 0.5、泛化 1，留白度 0.75 → 机会分 0.64，进 3 簇建议。同期泛词“erp”虽 S 档但结果页全是巨头官网（真空度低），不花探针钱。

### 10.2 接入输入（第 0 周，五类）

| 类 | 具体信息 | 用在哪 |
|---|---|---|
| 合同/租户 | 名称、mode、套餐、期限 | ⑫ |
| 品牌与行业 | 品牌名、行业（导入行业模板：种子表/竞品词表/白名单）、市场（定模型清单） | 管道配置 |
| **品牌词表** | 本品牌名+品线+型号+别名+竞品清单 | 提及判定与竞品占位的依据——没有它 72 条回答判不了“谁被提到” |
| **官方口径** | 官方价格、参数、适用边界、服务承诺 | 错答判定的比对基准——不收它，诊断包一半结论出不来 |
| 成员与授权 | 角色名单；C 类数据书面授权与对接方式 | 权限矩阵；合规 |

### 10.3 实现说明

**采集段**（唯一有外部依赖的部分）：

| 源 | 实现方式 | 要点 |
|---|---|---|
| A 检索热度 | Google Trends 无官方 API：pytrends（非官方库）或 SerpAPI / DataForSEO（付费兑底）；百度指数走 5118 等付费 API | pytrends 免费但脆（限流/改版即断），重试+缓存+付费兑底 |
| B 平台内 | 各平台搜索框的 suggest 接口 + 热榜半公开接口，浏览器等价的低频采样；**MVP 人工+半自动（不写自动爬虫），V1 做适配器** | 遵守平台条款；可被人工采样替代 |
| C 自有数据 | 客户数据集成：MVP CSV 导入，V1 webhook/API；入库前脱敏 ETL | 打通成本在集成不在抓取 |
| SERP 真空度 | 付费 SERP API（约 $1–2/千次）取前 20 条结果构成 | 不自建搜索结果爬虫（反爬极强） |

**处理段**（纯内部代码）：归一化（大小写/标点/简繁）→ 精确去重 → 归簇（MVP 规则辅助人工确认；V1 句向量+聚类+LLM 命名打标，人工抽检）→ 分档（行业内 `demand_index` 算 P50/P75/P90）→ 快照原子落库。**簇 ID 稳定性**：每周重聚类簇会变，但 `cluster_id` 不能乱变（问句池、SOV 曲线都挂在它上）——新簇与旧簇按代表词重叠度匹配，超阈值沿用旧 ID；真拆并才开新版本（§3）。

**MVP 切分**：人工只在外部取数（TrendsBar/5118 导出、人工记联想、客户工单导出）；**从 CSV 导入 `keyword_raw` 那一刻起全链路系统内自动**——外部最脆的部分用人力扛，核心逻辑从第一天就是可验收的代码。

### 10.4 产品化要点

- **种子表管理**：每行业一张，行级维护人 + 复核时间；生成语法模板内置，一键批量造词。
- **采集管道**：A/B 周级、C 事件触发、D 月级；界面固定显示“数据截至 X · 下次刷新 Y”，对外 SLA 只承诺周级。
- **飙升告警**：新词首见 <14 天且连续两周上升，推送给策略角色，进候选预筛。
- **机会看板**：意图簇 × 留白度热力图，红区一目了然；候选簇经“热度档 + 结果页真空度”双筛后才跑探针（省探针钱）。
- **机会卡**：需求层的唯一出口对象，带全部版本号（`pool_version`、`snapshot_id`）与 ID，机会分与渠道信号分别读自 `cluster_score` 与 `cluster_platform_signal`。

### 10.5 跨行业情报墙（P1·内部工具侧）

③ 机会看板的全租户跨行业读投影（每行业 ≤10 条值得看的信号：新簇冒头/档位环比/告警/竞品新占位）+ 每周一 digest（周批跑完自动生成"上周雷达变化"摘要，内部对象不经审核队列、不出客户报告）。
归 P1 内部工具，不进对外功能与验收清单。

## 11. 生产层设计

生产流水线：`机会卡 → 选题（一卡一文或一卡多文）→ 大纲（挂意图 + 必填事实块）→ 事实块撰写 → 事实校验 → 平台适配建议 → 审核放行 → 发布登记`。

生产层对外开放（v3 起不再只对内）：

- **事实块编辑器**：内置可引用四问校验——没数字、没口径过不了提交；每块强制绑定来源；**意图必配块类型是提交闸门**（§6）；另有两级机械校验——段落自包含（禁悬空指代）与跨平台口径冲突报警（§6）。
- **来源灯**：L1/L2 绿灯放行；L3 直接红灯，不给提交。
- **审核流**：FactCheck 唯一放行；谁写、谁改、谁放行全程留痕（写的人和放行的人不能同一个）。
- **模板库**：按意图六类给写作模板，客户下载后在自己渠道用。
- **发布登记**：客户在自己渠道发布后回填时间与 URL，系统只记录、不校验、不代发。
- **渠道适配建议**：按机会卡的渠道信号（§7）生成本簇适配清单——官网的 DOM 区块与 FAQ Schema、知乎的组织方式；偏离建议渠道的发布会被记录，供回流分析。
- **不做**：自动分发、代发、多平台一键群发（V1.x 评估）。

对内种子案例（`self` 模式）跑整包全链路含发布，但发的是我方自己的站，走运营手册，不进产品功能。

## 12. 验证层设计

### 12.1 探针的三种出场时机

| 场合 | 覆盖范围 | 目的 | 节奏 |
|---|---|---|---|
| 评分批次（首次 = 基线 T0） | 全部候选簇（MVP 30 簇） | 留白四分 + 建立基线 | 月度；接入期加急（基线 10 个工作日交付的来源） |
| 事件复测 | 目标 3 簇 + 对照 3 簇 | 动作后差值 | 客户发布后 D+3/14/30 |
| 月度全量 | 30 个监测簇 | SOV 月报、新簇评分 | 每月 |

**一次采样、两份产出**：首次探针的 72 条回答，读法一产出留白四分（喂机会卡），读法二产出提及率与占位（SOV 基线 T0）——机会卡上的“竞品占位 1”和诊断包里的“贵司零提及”是同一批回答的两个视角。§14.2 成本表里基线 2,160 次只算一次的原因。

### 12.2 引用判定管道（核心算法）

判定完全发生在我们这侧——AI 不知道自己在被追踪，内容里也没有可埋的追踪码。每条 `probe_result` 过四步：

1. **品牌提及**：品牌词表匹配（纯品类词不算点名）→ `brand_mentioned`；
2. **显式链接抽取**：搜索接地的模型常在回答里列来源——抽出来与登记的 `content_asset.url` 比对，**链接直接命中是最强信号**，同时记 `cited_domains[]`（也是 §7 簇级渠道信号的原料）。引用的两种形态都要抽：网页端是脚注/来源卡片，API 联网工具返回的是结构化 citation 元数据——适配层归一化后再进判定；
3. **指纹匹配**：回答分段后与本品牌所有块的指纹（关键数字+单位+专名）比对——模型改写文字（“8至12周” vs “8–12 周”）只要数字组合与专名还在就能命中 → `cited_claim_ids`；
4. **语义兑底**：指纹未中但段落与某块语义相似度超阈值（模型大改写）→ 标疑似引用，进人工抽检，不直接计数。

**两级引用分开记**：显式引用（带链接，客户报表的硬指标）与隐式引用（改写命中指纹，内部分析）。**“引用了哪一段” = 命中哪个 `claim_id`，块级粒度**——这是三个归因问题（§8）能被回答的前提。

### 12.3 界面与工单

- **基线管理**：每品牌每期一套基线快照；任一在测模型主版本变化，自动触发全量重跑并标"基线重置"。
- **复测台**：问句 × 模型 × 时点矩阵，格子显示提及 / 引用 / 错误，点开看原始回答与命中的 `claim_id`。
- **报告页**：月度 SOV 与事实准确率，一键导出；差值计算自动校验快照口径，不一致直接标"不可比"，不出差值。
- **回流工单**：每个复测批次落库后，信号检测 job 按五类阈值规则（§8）扫描，触发即生成工单（带信号、证据 `probe_id`、责任角色、时限，"说错"类红色 24 小时）；周一 30 分钟评审会处理"立即"类，月度批次随报告出完后 3 个工作日完成。

**左侧导航与页面清单**：

| 分组 | 页面 | MVP |
|---|---|---|
| 总览 | 工作台 Dashboard | ✓ |
| 诊断 | 诊断交付台 | ✓ |
| 机会 | 机会看板（含机会卡抽屉） | ✓ |

菜单按角色显隐：**客户（full 档）**见 总览 / 诊断 / **机会（本品牌簇的筛选只读视图）** / 内容（工作台、模板库、发布登记）/ 验证（复测台只读、报告页）/ 证据（证据包）；**diagnosis 档**客户不见“机会”，市场视角由诊断包承载；**我方内部**全量。

**全局交互规则**：

1. **任何结论可回溯**：点任何数字 / 结论都能回到 `probe_id` 与来源等级——"可复核"要落到交互上，不能只写在合同里。
2. **口径可见**：所有对比带快照口径徽标，版本不一致显示"不可比"灰条，不出差值。
3. **状态先行**：每个对象带状态标签（草稿 / 待审 / 已放行 / 已发布 / 待复测 / 基线重置 / 不可比）。界面可以少，状态不能糊。
4. **客户端默认只读**，可编辑区仅内容工作台（Editor / Content 角色）。
5. 桌面优先（≥1440 宽）；移动端只有日报卡片（今日新增错误、待审项、飙升词）。
6. 空状态引导新租户走"建种子表 → 跑基线"第一步；探针失败显示重试次数，不静默吞错。

### 13.2 各页面设计

每页按"组件 / 功能 / 权限要点"描述。

**① 工作台 Dashboard**
- 组件：KPI 卡行（SOV、事实准确率、引用率、待办数）｜月度趋势图（SOV 与准确率双线）｜待办列表（审核、复测、回流工单）｜告警流（飙升词、模型版本变更）。
- 功能：一屏看健康度；KPI 卡与待办均可点击跳转对应页面。
- 权限：客户 Viewer 也可看（限本品牌）。

**② 诊断交付台**（对外核心页）
- 组件：结论卡列表（每条 = 簇名 + 热度档 + 留白分 + 一句话结论 + 回溯链 + 来源灯）｜"建议先做的 3 簇"大卡区（选择理由、证据数、模板下载）｜导出 PDF。
- 功能：每条结论可点开水印证据摘录弹层；客户在此确认 3 簇，或一键提异议（异议生成复核申请单）。
- 权限：客户 Owner 确认 / 提异议；Editor 可下载模板与证据包。

**③ 机会看板**
- 组件：筛选栏（行业 / 意图 / 热度档 / 真空度 / 状态）｜意图簇 × 留白度热力图（红 = 高热度 + 高留白）｜簇列表（列：簇名、`demand_tier`、四个 `*_score`、`serp_vacuum`、样本状态）｜机会卡抽屉。
- 功能：红区识别；点簇开抽屉看机会卡全貌（版本号、机会分及构成、探针样本量）；"待补测"簇显示样本不足标记；建卡按钮仅策略角色可见。
- 权限：客户端（full 档）只给本品牌相关簇的筛选只读视图，竞品仅聚合层；diagnosis 档客户不进此页，市场视角由诊断包承载。

**④ 种子表管理**
- 组件：词根表格（词 / 类型 / 维护人 / 复核时间 / 状态）｜生成语法面板（模板下拉 + 批量生成预览）｜版本历史。
- 功能：行级编辑必填维护人；一键按模板批量造词；无维护人行红色警示；C 类问句回灌入口。
- 权限：仅我方策略角色可写。

**⑤ 内容工作台（事实块编辑器）**
- 组件：双栏——左侧事实块树（按意图分组 + 状态标签），右侧编辑器；编辑器含结构化字段（数字 / 单位 / 口径 / 边界 / 来源 URL）、来源灯徽标、可引用四问校验面板。
- 功能：每块强制绑来源，L3 红灯不给提交；四问校验不过不给提交；提交进审核队列；改块开新版本，不覆盖旧版。
- 权限：客户 Editor 与我方 Content 共用，按署名区分作者。

**⑥ 审核队列**（FactCheck）
- 组件：待审列表（事实块 / 证据包两个 tab）｜diff 视图（新旧版本对照）｜来源原件预览｜放行 / 驳回按钮（驳回必填理由）。
- 功能：唯一放行权；驳回自动回作者；全程写 `audit_log`；"写的人不能放行"由系统强制——同人时放行按钮禁用。
- 权限：仅 FactCheck。

**⑦ 模板库**
- 组件：按意图六类的模板卡片网格｜预览｜下载。
- 功能：模板内嵌来源占位符，与证据包关联；客户下载后在自己渠道使用。

**⑧ 复测台**
- 组件：问句 × 模型 × 时点矩阵（格子三色：提及 / 引用 / 错误）｜时点选择器（T0 / D+3 / D+14 / D+30 / 月度）｜格子抽屉（原始回答 + 命中 `claim_id` 高亮）｜对照组角标。
- 功能：前后对比自动校验快照口径，不一致整块标"不可比"；登记发布后自动生成 D+3 / D+14 / D+30 复测排期。
- 权限：原始回答仅我方内部可见；客户端格子只显示判定结果，原文走异议复核通道。

**⑨ 报告页**
- 组件：月度报告（SOV / 准确率 / 引用率趋势 + 目标簇前后差值 + 对照组对照）｜披露条（"内容由我方生产"自动标注）｜分母变更标注｜导出 PDF。
- 功能：对外汇报主出口；差值只在快照口径一致时给出。
- 权限：客户 Owner / Viewer 可看可导出。

**⑩ 发布登记**
- 组件：登记表单（簇 / 内容资产 / 发布时间 / URL / 平台）｜登记列表。
- 功能：客户回填发布信息，系统只记录、不校验、不代发；登记后自动生成事件复测工单。
- 权限：客户 Editor 填写。

**⑪ 证据包 / 异议复核**
- 组件：证据包列表（封版状态）｜证据条目（结论 + `probe_id` + 来源等级 + 摘录）｜水印查看器（只读、显示调阅人、禁导出）。
- 功能：CS 陪同下调阅单条原始回答摘录；**批量导出入口在界面上就不存在**——"单条可查、批量不可导"是设计约束，不是流程约束。
- 权限：客户经异议通道；全程写 `audit_log`。

**⑫ 设置 / 审计**
- 组件一：租户级"开通清单"卡，五步状态灯：① 租户信息 → ② 成员与角色 → ③ 品牌 → ④ 判定词表 → ⑤ 官方口径。卡底"基线可开跑"总闸字段 = 词表已封版 AND 口径 ≥1 条 approved。
- 组件二：每步表单。② 我方成员按"生产套餐（Strategist+Content+Evidence）/审核套餐（FactCheck+CS）"快捷绑定，客户角色下拉互斥组合置灰，Owner≥1 才绿；③ 行业选择联动行业模板预填（种子表骨架/竞品候选/白名单初稿），市场选择联动模型清单并提示"T14 当日复核联网能力"。
- 组件三：④⑤ 为"预填确认"交互。系统（接入预填，见 §15.2）按官网抓取+LLM 起草词表与口径草稿，每条挂来源 URL，人工逐条确认/修改/删除；采不到的条目明示"⚠ 需客户提供"，一键生成清单发 Editor。封版动作不在本页发生——提交后显示"待封版"+链接去 ⑥ 队列（通用队列 object_type 已含 brand_lexicon/official_fact）。
- 交互规则：词表/口径修订都在本页改"v2 草稿"再走队列，版本切换时界面明确提示"基线批次继续按 v1 判定、下批次起用 v2"；基线总闸 UI 禁用只负责引导，服务端硬校验配套（probe_batch.create/start 须有该品牌已封版词表与 ≥1 条 approved 且已生效官方口径，否则 422 judgment_basis_missing；C1 裁定见 API 规格）。
- 保留设置能力：成员与角色管理、审计日志检索（谁、何时、看了哪个 probe_id / 哪条 C 类数据）、模型与配额管理。
- 权限：Admin 全量；租户 Owner 可看本租户成员；封版仅走 FactCheck 审核队列，写与放不能同人。

### 13.3 用户旅程：一个客户的第一个 10 周

设场景：B2B 软件客户签约后（对照 §14.3 里程碑）。主角：客户 Owner（决策）、客户 Editor（执行）、我方团队。

**第一幕 · 接入与基线（第 0–2 周）**
我方在 ⑫ 建租户与角色（权限矩阵自动裁剪菜单），策略在 ④ 建 B2B 种子表并开管道，飙升告警开始往顶栏铃铛推新词。接入收五类输入（§10.2）：种子与行业、品牌词表（提及判定全靠它）、官方口径（错答比对基准）、成员与角色、C 类授权。第 2 周候选簇筛出后配问句、冻进问句池，加急评分批次跑基线——一次采样同时产出留白四分与 SOV 基线（§12.1）。客户第一屏是 ①——KPI 卡标“基线进行中”，顶栏“数据截至 X · 下次刷新 Y”先立预期：这是周级产品，不是实时监控。第 2 周末 Owner 打开 ②：结论卡逐条可点回 `probe_id` 与水印摘录，底部“建议先做的 3 簇”大卡。**Owner 只做两个动作**：确认这 3 个簇，或提异议（走 ⑪ 单条调阅，CS 陪同）。

**第二幕 · 生产与放行（第 3–5 周）**
Editor 主战场 ⑤：结构化字段 + 来源灯 + 四问校验，没数字保存键是灰的；没思路去 ⑦ 拿模板；服务档客户由我方 Content 在同一工作台代写（作者标记区分）。提交进 ⑥，FactCheck 看 diff 与来源原件，放行或驳回（驳回必填理由，自动回作者）；同人写同人放，放行按钮禁用。

**第三幕 · 发布与复测（第 6–8 周）**
发布在客户自己渠道（官网、知乎、行业站），回 ⑩ 登记时间与 URL——⑧ 自动长出 D+3 / D+14 / D+30 排期。复测台矩阵三色 + 对照组角标；D+3 大概率无变化，预期管理已在报告与话术里打好预防针（效果以月计）。月末 ⑨ 出首份月报：趋势 + 目标簇前后差值 + 对照组对照 + “内容由我方生产”披露条，一键导出。

**第四幕 · 循环（第 9 周起，产品常态）**
① 变日常枢纽：回流工单带责任与时限（“说错”类红色 24 小时）；策略盯 ③④ 与告警，周一 30 分钟评审；Owner 月度看 ⑨，Editor 周看 ⑧、日常在 ⑤⑩。

**角色动线一览**：

| 用户 | 页面 | 频率 |
|---|---|---|
| 客户 Owner | ②（确认/异议）、⑨（月报）、① | 月度 |
| 客户 Editor | ⑤、⑦、⑩、⑧（只读） | 日常 |
| 诊断档客户 | ② + ⑧ 只读 + ⑨，全程不碰编辑 | 一次性 + 月度 |
| 我方内部 | ③④⑥⑪⑫ 全量 + 周一评审会 | 每日 |

**设计意图**：客户全程只需学会四个动作——看诊断、确认簇、写事实块、登记发布；判定、评分、排期、归因、回流都由系统与我方承担。销售口径：“您方每月花在系统上的时间不超过两小时。”P2 起用户可以不打开网页，直接对桌面 Agent 提问（§16）——入口会变多，对象流不变。

### 13.4 工作室自运营剧本（dogfood）

产品正式对外交付前，工作室把自己当第一个租户跑全链路。本剧本是 §13.3 客户旅程的内部镜像：流程、角色、口径与对外交付完全一致，但服务对象是自己的产品与品牌。它不改变任何一条验收承诺——"一个真实客户"的验收位置不因此取消（§14.1）。

定位：①养熟流程；②生产销售素材（每条案例的可回溯证据包=给客户看的证据包）；③自建品牌资产。不是第四条产品线。

#### 13.4.1 租户与角色

自建租户，内部配额口径；写与放的分卡同外部规则一致（FactCheck 不由任何写内容的人兼任）。
每个工具/新产品 = 一个新品牌条目（品牌词表收产品名、缩写、GitHub repo 名及别名）；多行业 = 多条行业管道，自运营只消费产能。

#### 13.4.2 双机会簇判读

| 机会类型 | 看什么 | 决定什么 |
|---|---|---|
| 内容机会 | 留白分（空白/泛化/错答）+ 真空度 | 第 4 幕解析文写什么 |
| 产品机会 | 需求档位 + 问题型/痛点型簇密度 + C 类工单反复抱怨 | vibe coding 做什么 |
| 双机会簇 | 档高 + 痛点集中 + 真空高 | 一把抓两个动作：v0.1 工具 + 解析文，同簇同周期互相放大 |

留白低 ≠ 没产品机会；需求低 ≠ 没文章机会。只有双信号才同时立项。

#### 13.4.3 循环节奏（单案例 ≈ 6 周，多案例并行错相）

| 时点 | 动作 | 对应幕 |
|---|---|---|
| 周 0 | 配置（词表 v1 + README 口径 → 队列封版）→ 词池日发现双机会簇 | 第 0/1 幕 |
| 周 0–1 | 冻结问句 + freeze 快照 + 建基线批次 → 跑完 T0（SOV=0）——必须在发布前完成 | 第 2 幕 |
| 周 1–2 | vibe coding，上 GitHub | — |
| 周 2 | 写解析文 → 审核 → 发布 → ⑩ 登记（自动排 D+3/14/30） | 第 4 幕 |
| 周 3–5 | 沙盒期：D+3/D+14 大概率零，属预期，禁止中途改口径或加码 | — |
| 周 5–6 | D+30 复测出首个读数；月度报告出差值 | 第 5 幕 |

并行原则：同时 2–3 个案例错相跑（上限 3，具体并行数按当时人力调节），SOV 曲线按时序错开、各自可归因；吞吐由并行簇数与复测额度决定。基线一生只跑一次；发布一周后手动摸底只许走月度校准轨的人工抽检，不动复测。

#### 13.4.4 数据与口径注意

开源产品的官方口径现成：README 功能/边界/支持范围即 L1 来源；价格条目按产品实际结构填：全部免费开源的工具填“免费开源、无付费承诺”，开源+商业双轨的填实际价格结构与边界，不允许空置。
工具与解析文双投放同簇时，§8 组合效应栏正是归因位。
每个新产品从零基线起步，案例叙事自动获得"从 0 到 x%"最干净的对比。

#### 13.4.5 复盘北极星

两个 KPI 分账号看，不互相扣锅：

| 问题 | 读数口 | 节奏 |
|---|---|---|
| 市场还在涨吗（需求命中） | 词池周报：簇档位环比、问句回流 | 每周 |
| AI 开始提我了吗（GEO 效果） | 复测差值：引用率/SOV vs T0，对照组对照 | D+30 起月度 |

最终北极星：工作室品牌名月度 SOV 曲线（主指标，N 个案例后应单调向上，跑平则说明簇选择方向错而非执行差）；辅助过程 KPI：全案例合计簇级引用总量（诊断口径）。理由：北极星押品牌推广终极目的，过程 KPI 押案例产能，两者分账互不扣锅。案例收官把证据包封版截图放对外案例页。

#### 13.4.6 分发实操（来源：独立站社区公开 SEO 方法，吸收改写）

目录站提交节奏：每周 5–15 条（Product Hunt / TAAFT / Futurepedia / 垂直目录），防止挤审核队列；

外链磁铁：开源数据表/好用小插件——开源产品本身就是磁铁；模型检索接地读的是搜索引擎索引，外链与权威度仍是 AI 可见性的前置，SEO 与 GEO 是叠层不是替代，解析文一份内容吃两份流量（GSC 点击 + AI 引用）。

#### 13.4.7 边界清单

不替代外部客户验收（§14.1 照原样执行）；
不改对外口径三纪律；
第 6 幕异议链在自运营无交互对象，其用途是案例页可展示证据包；
本节新增的自用工具（情报墙、digest、接入预填、日频热门词副信号）全归 P1 内部工具侧，不进对外功能与验收清单。

## 14. MVP

**只做 B2B 企业软件一个行业、一个客户，一条完整链路跑通。**（选 B2B 的理由：采购方已经在问 AI、决策链短、客户能看懂竞品占位。）

**做**：

1. 词库与意图分层（人工 + 半自动，不做全自动爬取）
2. 基线探针：30 簇 × 72 条 = 2,160 次采样
3. 缺口清单 + 建议先做的 3 簇 + 证据包与模板
4. **事实块编辑器 + 来源灯 + 审核流**（v3 新增）
5. 复测与 SOV 报表：事件复测 432 次/轮 × 3 + 月度全量 2,160 次
6. 一份可对外讲的种子案例

**不做**：代发与自动分发、多行业模板、线索归因看板（AI 线索 V1.x）、私有化部署、Agent 与 MCP 能力（路线与 13 条预留见 §15–§16，实现后置）。

### 14.1 验收标准

| 验收项 | 阈值 | 怎么验 |
|---|---|---|
| 基线覆盖 | 30 簇中 ≥ 25 簇 `n_valid ≥ 70`（结构 72 条/簇，拒答不计分母） | 查 `probe_result` 计数 |
| 3 簇建议样本充分 | 每簇 `n_valid ≥ 70` | 交付包逐簇抽样 |
| 诊断可复核率 | 抽 30 条结论，100% 能回到 `probe_id` + 来源；口径复核通过率 ≥ 95% | 人工抽样 + 审计日志 |
| 判定一致性 | 同问句同模型 3 轮判定一致率 ≥ 85% | 自动比对 + 10% 人工抽检 |
| 网页端偏差抽检 | 月度抽 5–10% 问句网页版复跑（Playwright 半自动 + 人工复核），与 API 检索轨的提及判定一致率记录并披露；连续两月 <70% 触发口径复核 | 半自动抽样 + 报告附录 |
| 客户可用性 | 客户 3 位评审对"3 个簇能否直接开工"打分均值 ≥ 4/5 | 交付后回访 |
| 交付时延 | 基线 10 个工作日内；D+3 当日、D+14/D+30 ± 2 天 | 工单时间戳 |
| 承诺合规 | 合同、报价、交付包中"排名 / 推荐 / 引用率承诺"字样 0 处 | 交付前 checklist 逐份签 |
| 成本上限 | 单客户月 API ≤ ¥300 | 配额告警 |

前三项（覆盖、样本、可复核）未达标不得交付，按内部返工处理。

### 14.2 成本（单客户 / 月）

口径：单次回答约 2.5k token，按国内主流模型混合均价 ¥0.03/次估算（±50% 浮动），是预算口径不是报价。

| 项 | 量 | 估算 |
|---|---|---|
| 基线探针 | 2,160 次 | ≈ ¥65（一次性） |
| 事件复测 | 3 轮 × 432 次 | ≈ ¥39/月 |
| 月度全量 | 2,160 次 | ≈ ¥65/月 |
| **API 合计** | ≈ 3,456 次/月 | **≈ ¥104/月，首月 ≈ ¥169；上限 ¥300** |
| 人力 | 策略 0.3 + 内容 0.2 + 证据 0.2 + 审核 0.1 + CS 0.2 = 1.0 人月/客户/月 | 首批 5 客户 ≈ 5 FTE |

**成本红线**：超 ¥300 先降“3 模型 × 2 轮”，仍超则减问句，降级写进交付说明，不允许静默减采样。（P0 起 judge 调用纳入同一配额，估算见 §15.3。）

### 14.3 里程碑

第 1–2 周词库与基线实测；第 3–5 周缺口清单与 3 簇建议；第 6–8 周复测出首份 SOV 报告；第 9–10 周复盘定模板。

# 15. 智能化：Agent 能力规划

> Agent 不进 MVP 验收，实现后置；本章是路线与预留，保证 MVP 之后接入不改产品骨架。

### 15.1 总原则与 Runtime 架构

总原则一句话：**Agent 提生产力，规则引擎保可信度，人机关卡一个不撤。**Agent 是被规则管着的执行者，不是规则本身。

```
┌────────────────────────────────────────────┐
│  Agent Runtime（横向层）                      │
│  统一鉴权 ← 角色权限矩阵   统一审计 → audit_log │
│  工具集 = 产品 API（受状态机与硬规则约束）      │
└──────┬───────────┬───────────┬─────────────┘
       ▼           ▼           ▼
    需求层        生产层        验证层
```

四条架构原则：**权限继承**（agent 以发起人身份行动，无特权角色，客户 Editor 的 agent 看不到竞品原始回答）；**只调工具不碰库**（走产品 API，冻结快照与封版证据包同样改不了）；**产出即对象**（草稿进编辑器、建议进审核队列，不造“AI 内容”孤岛；全局加 Agent 任务中心：跑了什么、依据什么、谁批准）；**动作留痕**（agent 动作是 audit_log 一等公民：谁发起、哪个 prompt 版本、读了什么、产出什么）。

### 15.2 三层能力清单

**需求层（分析 + 配置）**

| 能力 | 做什么 | 受什么约束 |
|---|---|---|
| 种子表副维护人 | 生成语法扩词、C 类回灌缺口监测、到点提醒复核 | maintainer 必须是人，agent 只建议 |
| 归簇与意图分层 | 归簇候选 + 六类打标，策略一键确认/驳回 | 无出处不进池 |
| 真空度判读 | 抓结果页前 20 条判构成，产出 serp_vacuum | 外部内容按不可信输入处理（§15.3） |
| 机会卡起草 | 从 cluster_score 生成“为什么是这 3 簇”结论卡草稿 | 结论必须挂 probe_id，不许自由发挥 |
| 接入预填 agent | 抓官网+SERP → LLM 起草品牌词表/官方口径草稿（每条挂来源链接）→ 人工确认 → 走审核队列封版 | 第 13 项；实现可先做内部半自动 job；人工确认是硬关卡，MVP 范围不破；归 P1 内部工具侧（§13.4.7） |

**生产层（编写）**

| 能力 | 做什么 | 受什么约束 |
|---|---|---|
| 事实块起草 | 读 L1/L2 原件，抽“数字+口径+边界+出处”填结构化字段 | 四问校验器是安全带：无来源不生成、L3 不提交；产出全进审核队列 |
| 大纲生成 | 按意图模板 + 必填事实块清单起草 | 硬映射表是模板，不许发挥 |
| 错答修正建议 | “被引用但说错”触发后定位错误、对比 claim_block、起草 diff | 修正同样过放行；24 小时时限适合 agent 先动手 |
| L3 来源预警 | 提交前查软文/无源转引 | 直接服务来源灯 |

**验证层（分析）**

| 能力 | 做什么 | 受什么约束 |
|---|---|---|
| 判定自动化 | 一次判四类留白 + 抽 high_err | 红线一（§15.3） |
| 错答清单生成 | 从回答原文抽“AI 把你的什么说错了” | 每条挂 probe_id 原文摘录 |
| 报告解读草稿 | 月报归因段落草稿（对照组、基线重置、分母变更标注） | 差值只在快照口径一致时给 |
| 回流分诊 | 五类信号初筛与动作建议，周一评审只看整理后的队列 | 评审会仍由人开 |

### 15.3 两条特殊红线

**红线一：LLM-as-judge 三规矩**。它是唯一“直接写判定”而非“出建议”的 agent：
1. **judge 模型与被测模型厂商隔离**——不能用 GPT 判 GPT，同源偏差会把留白度测歪；
2. **判定方式版本化**：prompt 进 `scoring_snapshot.judge_version`——换判定方式（正则→judge、换 prompt）= 开新快照 = 基线重置；
3. **持续校准**：“人工抽检一致率 ≥85%”从一次性验收变成持续运行的校准集，跌破阈值降级回人工。

成本：judge 每条回答跑一次，月 5,600–8,600 次调用，小模型约 ¥30–50/月，仍在 ¥300 红线内，但显式纳入 §14.2 配额，受同一告警管。

**红线二：提示注入隔离**。agent 要读大量外部内容（模型回答、结果页、来源文章），竞品完全可以在网页里埋“忽略以上指令”。所有读外部内容的 agent 一律按不可信输入处理：原始内容只作数据引用、不进 prompt 指令位，输出做结构化校验。已进 §9.4 风险表。

### 15.4 分期

| 期 | 内容 | 理由 |
|---|---|---|
| **P0（与 MVP 并行，不进验收）** | 判定 judge、事实块起草、错答清单生成 | 直接砍人力（1.0 人月/客户中判定与起草占大头）且提升诊断包质量 |
| **P1** | 归簇分层、种子维护提醒、回流分诊、报告草稿 | 提效锦上添花，依赖 Runtime 先跑稳 |
| **P2** | 配置类 agent（agent 成为口径守门员的对话界面）+ MCP 对外开放（§16） | 共享“产品 API 对外暴露”这一步 |

销售素材顺带一提：“我们产品里的 agent 产出的每一条内容都过来源灯和独立审核”——这就是“非注水 GEO”的活示范。

# 16. 对外接入：MCP 与桌面 Agent

### 16.1 架构：一个 API，三张脸

```
                 ┌─ Web 界面（人）
 产品 API（统一） ├─ Agent Runtime（内部智能体）
                 └─ MCP Server（外部/个人桌面 Agent：pi、Claude Desktop 等）
```

MCP Server 是产品 API 之上的薄适配层，不含业务逻辑。pi-mono 智能体办公室的团队 Agent 与客户的个人 Agent 连同一个 MCP Server（streamable HTTP + 令牌），靠 token 权限范围区分。pi 的 mcp.json 格式与 Claude Desktop / Cursor 兼容——做一次，全桌面 Agent 生态通用。

工具设计约束（源自客户端行为）：结果超 20KB 会被截断 → 工具做“摘要 + 下钻”两级；工具注解（readOnlyHint / destructiveHint）驱动客户端权限门 → 与我们的读写分级天然对齐。

### 16.2 三级工具映射

| 用户对 Agent 说 | 工具级 | 进系统的路径 |
|---|---|---|
| “这个月可见度怎么样” | 只读工具 | 查 metric_snapshot / cluster_score，返回带 snapshot_id 的结构化摘要 |
| “帮我写下季度内容计划” | 草稿工具 | 生成计划草稿 → 进审核队列，外部 Agent 无绿色通道 |
| “这 3 个簇先做哪个” | 提案工具 | 返回决策简报（机会卡对比、对照组差值、成本估算），拍板留给 Owner |

口径纪律同步到工具命名：叫 `get_sov` / `get_citation_rate`，不叫 rank——对外不出现“排名”。

### 16.3 MVP 预留清单（13 条）

判定标准：凡是“事后无法回填”的（历史数据语义、不可变快照字段、写路径架构）现在定；新功能新数据的以后加。十三条全是字段与架构纪律，零功能成本。

| # | 层 | 预留 | 不预留的代价 |
|---|---|---|---|
| 1 | 后端 | audit_log 加 actor_type(human/agent/external_agent)、agent_run_id、prompt_version | 审计只追加，历史“谁干的”语义无法回填 |
| 2 | 后端 | scoring_snapshot 加 judge_version，MVP 填 rule_manual_v1 | 快照不可变，漏了达条历史分数不可复现、基线全作废 |
| 3 | 后端 | 所有写操作走服务层 API + 服务端权限校验 | agent 工具集=产品 API；写路径散在页面里=重写全部写路径 |
| 4 | 后端 | 状态迁移做成显式 API 操作 | agent 动作=状态迁移；不显式就只能模拟人点按钮 |
| 5 | 后端 | 审核队列通用化（object_type + object_id） | 每加一种 agent 产出改一次队列结构 |
| 6 | 后端 | 配额按操作类型分粒度（probe/judge/drafting） | judge 调用量与探针同量级，混计无法单独限流 |
| 7 | 前端 | 审核队列按 object_type 动态渲染，不写死两种 tab | 后端 #5 的界面配套 |
| 8 | 前端 | “作者/来源”与“状态”两个正交维度展示 | 把 agent 起草做成状态而非作者属性，状态机分支翻倍 |
| 9 | 前端 | 告警流与日报卡片按类型可扩展 | agent 事件=新告警类型，不应改卡片组件 |
| 10 | MCP | per-user API 令牌与 Web 会话并存，权限矩阵同源 | MCP 唯一新增硬预留；后加要动鉴权中间件与审计语义 |
| 11 | MCP | 响应带口径元数据（snapshot_id/probe_id/数据截至）+ 分页 ≤20KB | 同时服务可复核卖点与客户端截断行为 |
| 12 | MCP | 操作语义分级（只读/草稿/提案）映射工具注解 | 显式状态机已分类，只需在 API 层暴露语义 |
| 13 | MCP | 配额按 token 限流 | 外部 agent 会轮询，与成本红线同一套计量 |

**明确不做**（防止提前过度设计）：MVP 不提前撒“AI 按钮”，不做对话/副驾面板预留，不建 Agent 任务中心页面——界面保持“工具 + 对象流”，agent 将来作为对象流的产生者自然出现。

预留收益：这十三条没有一条专为 agent 服务（多租户 SaaS 本该如此），agent 只是逼我们把“正确但容易被砍”的内部质量要求提前锁住。做到后，接内部 Agent 约两周量级，接 MCP 是一个适配层，都不动产品骨架。

# 第三部分 · 数据建模

## 17. 设计原则

1. **ID 链贯穿**：问句 → 机会卡 → 事实块 → 探针结果，全程带 ID 可互相追。
2. **版本链可倒推**：`seed_version → pool_version → question_pool_version → snapshot_id`，任何分数都能还原当时的输入；不在这条链上的分数不得进报告。
3. **单一出数口**：簇级分数只在 `cluster_score`；机会卡不复制分数字段。
4. **多租户隔离**：所有业务表带 `tenant_id` 行级隔离。
5. **引用判定用指纹**：每个事实块生成"关键数字 + 专有名词"指纹，命中即算引用——纯文本匹配会因模型改写而漏判。

## 19. 硬规则汇总

| # | 规则 | 出处 |
|---|---|---|
| 1 | 无出处不得进池：`question_pool` 溯源字段任一为空不入库；冻结后改动一律开新版本 | §3 |
| 2 | 同快照不覆盖：同一 `snapshot_id` 只追加不更新；冻结后采样参数不得改 | §4 |
| 3 | 样本不足不出分：`n_valid < 10` 或模型覆盖 < 3，`*_score` 写 null 标"待补测"，不许用 0 或均值填充 | §4 |
| 4 | 缺失模型不补齐：`model_coverage` 如实记，不折算 | §4 |
| 5 | 基线与复测必须同版本同快照；口径不一致标"不可比"，不出差值不进报告 | §3、§8 |
| 6 | 没有 maintainer 的行业不得启用管道 | §2 |
| 7 | 机会卡进生产队列前必须带 `demand_tier` 且 `demand_source` 非空 | §5 |
| 8 | L3 来源不进 `claim_block` | §6 |
| 9 | FactCheck 唯一放行；写的人和放行的人不能同一个 | §9.2 |
| 10 | 我方生产的内容，复测报告必须披露并带对照组 | §9.2 |
| 11 | 删簇只软删除，SOV 分母保留 90 天过渡 | §8 |
| 12 | 界面与销售材料不得出现"月搜索 X 次"与任何承诺性表述 | §2、§14.1 |
| 13 | 所有结论在界面上可点击回溯 `probe_id` 与来源等级 | §13.1 |
| 14 | 判定方式版本化：`judge_version` 进快照，换判定方式 = 开新快照 = 基线重置 | §15.3 |
| 15 | 外部内容（模型回答、结果页、来源文章）对 Agent 一律按不可信输入处理：只作数据、不进指令位 | §15.3 |
| 16 | 外部 Agent 与内部 Agent 同权限矩阵、同审核队列，无绿色通道；决策动作必须由人确认 | §16.2 |
| 17 | 问句池开新版本不自动作废已有簇的基线；可比性的单位是簇的问句集；升级问句必须人工拍板并重开基线 | §3 |
| 18 | 意图的必配块类型是提交闸门；块内禁悬空指代；同一数字跨平台口径必须一致 | §6 |
| 19 | 被测模型必须开启原生联网检索（检索轨）；换接地轨道 = 换快照 = 基线重置；同一快照内不混轨 | §4 |
